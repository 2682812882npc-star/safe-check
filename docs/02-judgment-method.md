# 统一判定方法

## 先定范围，再看值

每一项先写清平台/角色、基线版本、工作表及行号或CIS条目、检查对象、采集命令、目标值、适用条件。查询成功之后，再比较取得的当前值。

Windows使用[273项映射](mappings/windows-检查项映射.csv)，Ubuntu使用[九领域方法表](mappings/ubuntu-检查方法.csv)。这些表是原实验规则整理，不是目标机本次检查结果。

## 五类结论

| 结论 | 必要条件 | 常见误判 |
| --- | --- | --- |
| 符合 | 当次取得所需证据，所声明范围及层次均满足要求 | grep匹配一行、存在某配置就当作全部生效 |
| 不符合 | 已确认适用，至少一个成功取得的必要值偏离要求 | 缺工具或权限不足就直接当作不符合 |
| 不适用 | 当前角色/组件/选定方案满足排除条件，有理由及证据 | 不想检查或暂未安装就直接排除 |
| 未检查 | 未执行或查询失败，无法取得所需值 | 用旧截图、空输出或默认0补当前值 |
| 待确认 | 证据部分取得，但默认值、生效范围、业务用途等不足以定论 | 把所有待确认合并进符合数量 |

Ubuntu脚本还有“待核实”“待人工确认”“待确认适用”等细分文字。汇总到上述五类时保留原始文字及原因；未执行/失败归未检查，证据或适用性不完整归待确认。

## 三层验证

1. **文件/策略配置**：文件内容、注册表类型和值、SID完整集合、策略界面。
2. **有效/运行状态**：有效策略API、服务运行值、配置加载、监听和日志。声明值和运行值冲突时保留差异。
3. **功能及业务**：新SSH连接、成功sudo执行、实际共享签名、WinRM认证、ASR行为阻断及兼容性。未做第三层，不写“功能正常”。

离线测试使用构造数据验证代码如何判断，独立于这三层目标机验证。

## 人工复核顺序

1. 打开该项原始证据，核对时间、资产、命令、退出码、stderr、数据是否完整。
2. 核对版本、单位、类型和来源：KB/字节、分钟/秒、DWORD/字符串、配置/有效值不能混比。
3. 核对覆盖范围：SSH Include与Match、PAM引用和控制流、sudo Defaults作用域、HKCU用户范围、systemd覆盖顺序。
4. 依据明确偏差保留不符合；另有读取错误时并列记录，不能因为部分错误抹去已证实差异。
5. 需要业务策略的项目先确认用途/批准范围；例外单独记录，例外不改写原基线判定。

## 几个容易踩坑的地方

- 未匹配到配置，不一定等于查询失败或有效值不安全。区分“成功确认不存在”“配置未显式声明”“读取失败”，再查默认/有效值依据。
- 文件权限按禁止的权限位判断“不得宽于”，不能把更严格的0400/0600仅因字符串不同判错；属主、属组单独核对。
- 用户权限分配比较完整SID集合。LSA成功返回空集合才能表示“No One”；调用失败的空数组不能替代。
- APT版本与本地候选相同，只能证明与当前缓存一致；不能证明在线最新或已修复全部漏洞。
- 容器挂载目录出现宿主无名UID/GID，应先核对容器身份映射和业务范围，不凭路径或数字直接判通过。
- 运行值满足而持久配置缺失时，根据该条要求分别记录；不能保证重启后仍保持。

## 整改与复测

记录原值 → 确认改动对象与影响 → 准备本次备份和回退条件 → 核对备份 → 修改 → 语法/配置检查 → 必要时加载 → 新会话/功能验证 → 新证据目录留存。

复测使用新证据，不编辑原始报告来表示修复。回退后再次核对配置、权限和功能；恢复旧备份可能撤销其他已完成的加固。
